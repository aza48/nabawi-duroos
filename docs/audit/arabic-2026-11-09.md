### Recommended way to store Arabic versions without a migration

1. Code files keyed by slug, one per content type: `src/content/ar/guides.ts` and `src/content/ar/faqs.ts`, each exporting `Record<slug, { title; summary?; bodyHtml; checked: string }>`. Same for programmes (`src/content/ar/programs.ts` keyed by programme slug, mirroring the English fields) and discounts (an optional `dealAr` beside `deal` in `discounts.ts`, since it is one short line).
2. A single helper, for example `arabicGuide(row)` in `src/server/content/ar.ts`, returns the Arabic version when the slug exists and the row's `updatedAt` is not newer than the Arabic `checked` date; otherwise it returns the English row plus `fallback: true`.
3. When `fallback` is true the page keeps today's behaviour (English text in an LTR block, `EnglishNote`, canonical to English). When the Arabic version exists, the Arabic page drops the notice, renders RTL, uses its own canonical and `hreflang` pair, and gets added to the sitemap with `pair()`.
4. A test checks every Arabic entry's slug exists in the English seed, has no em or en dashes, and that every Arabic body keeps the same headings count as the English one, so a stale translation is caught when the English guide changes.
5. Because the bodies stay in code, the owner reviews translations in pull requests like any other change, and the admin editor is untouched. Moving them into the database later would need a `bodyHtmlAr` column and a migration.
